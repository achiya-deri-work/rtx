# What would actually buy 1.2× on the HOME 5090?

Start with D768/H256, not the tiny pools. Its measured gap is 0.788 ms versus the original 32-trial strong control. A faster **identical-hard-route** schedule on both paths leaves a 0.731 ms gap. Neither more ordinary trials nor fixing only routing makes this disappear. There is **no demonstrated 1.2× implementation** under these semantics. The useful target is a substantial change in the *routed backward*, accompanied by a fair, fast common router.

## Time budget, not a sum of microbenchmarks

RTX 5090 GPU0 / 170 SMs, Torch 2.13/cu132, final [hybrid study](mxfp8_hybrid_tails_20261119.md) runtime digest `487c4ce2bb3c4b915e34e3ac14249aab18ebd7137744042d81821b08bc08298d`. Median of round medians, milliseconds, from [the four result32 files](../autotune_reports/mxfp8_hybrid_tails_20261119/matrix5090). E and S below are *independently timed* MX expert and shared F+B, not disjoint in-layer timestamps. R = MX−E−S includes routing, graph/context differences, leaf work and interactions.

BF16 independently timed E/S: 2.2353/.4178, .3644/.1239, 2.6119/.5701, .0758/.0266 respectively. Native trails BF16 in *both* branches on D384. If both native branches became twice as fast and the residual stood still, predicted whole ratios would be 1.273, 1.099, 1.375 and 1.061. These are sensitivity models, not claims about hard physical lower bounds. Improving the shared branch alone, even to zero time, cannot cover any gap in the table.

If C is the same latency cut for both precisions, the new native-only cut needed is
`(MX−C)−(BF16−C)/1.2 = gap−C/6`. Even removing the **entire** measured 3.4042 ms isolated D512 router would only reduce its deficit by .5674 ms under this additive model. The four numbers for C needed with *zero native improvements* are 5.57, 2.82, 4.73, .746 ms; the D384 numbers even exceed whole native time. Where BF16 is already faster, eliminating equal work makes the ratio worse. For two same-semantic paths, faster routing is a product win, not a precision-specific win.

## What is actually matched?

[BF16FFNReference](../benchmarks/benchmark_moe_checkpoint.py) invokes the same learned router outside the reentrant expert and shared checkpoints. It passes the same registered weights, ids, inverse and differentiable weights into the BF16 reference. Both include per-sequence balancing, fixed K, output combine, input gradients, every trainable leaf, fresh gradient reset, packed weight views and final BF16 boundary. [Driver](../benchmarks/benchmark_moe_varlen.py) compiles both whole modules fullgraph/static with aggressive supported options, dynamic weights and outer warmed CUDA graphs. BF16 seven-GEMM shared trace verifies recomputation. Expert-only uses frozen differentiable routing weights and an FP32 upstream ABI; it is diagnostic, not a substitute for full module time. Training convergence, optimizer latency and identical BF16/MX values are not claimed.

**The router is matched but was not tuned in the matrix:** all four result32 configs have zero packed column shards, row-major hard quantiles, and router budget zero. Fresh ordinary-event D512 router measurement (three visits × seven samples, same original hashes for all parameters, X/dY and hard routes): router F+B 3.4042 ms, hard projection alone 1.7076 ms, transport fwd/bwd .8876/.5834 ms, metadata step .0512 ms. The whole residual 3.8180 ms overstates the independently measured router by .414 ms. That difference is not a free fusion opportunity. No router profiler injection.

D768: changing only quantile key layout to existing `expert_keys` gives MX 5.4626 ms, BF16 5.6779 ms (1.0394×); isolated router 2.2892 ms. Every recorded hash including inverse matches the original matrix, and expert/shared configs are unchanged. Original→keys is a cross-process comparison, not an interleaved isolated speedup. Adding four forward/backward Sinkhorn shards yields ~5.40/5.62 ms but changes hard-route hashes for the original input: **not accepted as fixed-route improvement**. Different FP32 reduction order can matter to discrete selection. Compare identical routers on both sides, and verify metadata; do not weaken the assignment rule to get a win.

All four original-router probes now have exact matrix input/parameter/hard-route hashes. The measured router F+B times, in table order, are **3.4042, 1.6732, 2.6541, .3596 ms** (~54%, 67%, 45%, 71% of original MX). Each is an isolated compiled phase with independent upstream route weights. On D768 the fresh original-router whole controls were 5.8272 MX / 6.0418 BF16: exact keys removed **.3646 ms MX and .3638 ms BF16**, almost exactly the .3649 ms router-only difference. The remaining native gap went from .7924 to .73096 ms, just as the one-sixth rule predicts. On D384/8224 hard selection and transport fwd/bwd took .7947/.4459/.2928 ms; on original D768 they took 1.3212/.6882/.4464 ms. This is a shared floor measured in milliseconds, not an assumption that fixed router costs make 1.2 physically impossible.

## Capacity and actual exposed work

For E experts and capacity C, real occupancy averaged over experts is T×K/E. All four physical capacities already equal the sum of block-32-rounded per-pool capacities. The ratios EC/(TK) are **1.020, 1.058, 1.039, 1.500** respectively (C=2240,1088,1600,96). No empty 32-row slab can be dropped on these fixtures without crossing independent pool block boundaries. At 512 tokens, 64-row tiles round C=96 to 128 executed rows: 2× real average 64, while selected short-dW K32 executes three groups, 1.5× real. At D768, ordinary 64-row down uses 7200 CTAs (42.4 one-resident waves), gate-dX 14400 (84.7); tiny down/dX each 384 (2.26). D512 down 17920 (105.4); D384/8224 down 1632 (9.6). Counts = E ceil(C/Mtile) ceil(D/Ntile) for selected one-tile/nonpersistent schedules, not measured occupancy. More SM-wide parallelism cannot be the general large-case explanation. D512 and both D384 downs have only one K128 macro stage, D768 two; a deeper copy pipeline cannot overlap a nonexistent next stage.

Exact-key D768 frozen-expert timeline, ordinary graph ~2.32 ms. Forward gate+up 222 µs, down 123, combine 79. Backward joint recompute **339**, route-gradient GEMM+reduction **290**, gate/down dW **310/153**, gate/down dX 164/86, final gather dx 84. Preparation: forward portfolio/gather 48/35; backward portfolio/gather 112/44, routed dual-orientation dY 125, indexed X transpose 70 µs. An additional copy is 33 µs; do not automatically attribute it to production routing. Stages are identified by launch order against [the plan builder](../rtx/_moe_execution.py). These are trace observations, not added to an unrelated whole graph. Public graph already amortizes host launch; prior shared trace coverage >99.6%. Shared computation is independent of route construction until the final add, but even perfect free overlap of the *entire* native shared step is below the target gap, before SM/bandwidth contention and the need to offer BF16 the same optimization. No client streams/private capture proposed.

The D768 backward joint producer writes four independent FP8 arrays and their E8M0 scales: hidden both ways + gate derivative both ways = 6×EC×H×33/32 = **121.65 MB** before rereads. One routed D-wide FP8 orientation is 60.83 MB; two for dY need 121.65 MB. Global per-token row quantize+gather already avoids computing the same row maximum K times; X-transpose along expert slots cannot reuse the feature-block scale. Forward and backward separately prepare weights/input, consistent with recomputation. Full slot-major BF16 write then read for an extra D-wide intermediate costs 235.93 MB logical; actual DRAM may be lower. No new hardware-counter claims. Dynamic weight changes rule out persisting packed weights without an explicit validity contract. Keep forward activations out of backward.

All D768 final 32 expert journal entries used **unsplit dW**; 32 trials of a mixed portfolio do not exhaust stage geometry. Gate/down dW grids already have 4608/2304 64×64 CTAs (27.1/13.6 one-resident waves). A two-way FP32 split adds **151.0 / 75.5 MB** workspace respectively plus write/read traffic and reduction; only use it if the reduced K critical path pays for that. The final BF16 cast must happen after FP32 reduction; preserve tail and existing split legality. Tiny has its short-K implementation already.

## Two causal probes narrow the next design

* **Route adjoint:** same compiled router, inputs, hard routes and frozen expert config, changing only fused → separate. Separate recomputed down took 131 µs plus 143 µs to read its BF16 slot outputs and dot with dY, versus fused 289+1 µs. Whole 5.4418 vs 5.4626 ms; standalone expert 2.3315 vs 2.3196 ms, i.e. opposite sign. No promotion: fresh-process effects are of similar scale, and replacing the fused operation clearly does **not** recover the entire difference between the 123 µs forward down and 290 µs fused adjoint. A composition harness first refused an eager vs compiled inverse hash; no result from that attempt was admitted. The ordinary compiled driver reproduced the exact original hashes. For a future interleaved harness, compute and verify the reference metadata with the same compiled router.
* **dW tile-reuse control:** double only Ntile on both dWs (64→128); same K, partitions, direct stores, dtype, registers policy and other legs. Gate/down dW **310/153→389/213 µs**. Whole **5.4626→5.6059 ms**, BF16 stable at 5.678 ms; expert 2.3196→2.4438 ms. FP64 quantized oracle worst NRMS 0.0103%, live growth zero, identical hard-route hashes. Reject this larger tile, not the entire class of dW work. Simply increasing nominal reuse or halving grid size was counterproductive.

## Ranked engineering work

Anchor the next work to exact-key D768. The ranges below are **screening estimates conditional on success**, derived by applying explicit fractions to measured stages, not observed savings or transferable gains. An implementation can regress. Save time in the total graph or reject it.

1. **Change ownership of backward preparation and recompute.** These stages collectively expose ~688 µs (backward portfolio/gather, routed dY, indexed transpose and joint recompute). First prototype a consumer that builds the *transposed X* block within gate-dW: a CTA owns a strip of D features across complete 32-slot expert blocks; vector-load the original BF16 X via the existing indexed map, derive its independent E8M0 scale, feed packed fragments directly. Keep qP-transpose as the existing operand. Compare against the current standalone indexed transpose **plus** gate-dW, not transpose time alone. A parallel axis is a tile-local joint recompute with dedicated warp ownership for writing the two independently scaled orientations; preserve BF16-decoded hidden and BF16-rounded derivative before transposed quantization. Compare against existing dual-operand scratch reuse, which already fuses these products. Only extend to routed dY once operand reuse outweighs repeated indexed loads. New compiler-visible buffers only if required; no forward→backward saved state. Gate tile strip × slot blocks × number of feature tiles per gather, quantizer layout and dedicated-vs-shared producer roles are structural axes. Reject if gathering/amax repeats per output tile enough to increase actual time, or if low-occupancy/scratch cliffs erase the cut. A 15–30% improvement over the listed preparation/recompute time is **.10–.21 ms**; there is no evidence for such a cut yet.
2. **Give the route-adjoint dot and routed movement an independent memory-access schedule.** Current route kernel has MMA lanes fetch unweighted FP32 dY at accumulator coordinates and convert each accumulator to BF16 before its dot. Test a dedicated cooperative vector loader for the token's contiguous dY tile, broadcast the slot→token mapping once per row group, exchange into accumulator lane order, and reduce partials with one owner. Tune the *adjoint* output tile/warp layout independent of forward down; compare both existing fused and separate controls. Extend the same routing-map locality idea to forward combine/backward dX only after the adjoint wins. No shortcut via dY×W then dot hidden: moving the required BF16 rounding changes the gradient. No global non-deterministic BF16 atomics. The route kernel's ~167 µs excess above regular forward down is an optimistic comparison, not removable time. A 20–35% cut to its 290 µs is **.058–.102 ms**; saving 15–25% of the two 163 µs movement legs would add **.024–.041 ms** only if it survives combined timing. Require exact routes and unchanged gate on output, route/input and all weight gradients, zero postwarm growth, no unacceptable scratch increase.
3. **Test persistent unsplit dW operand reuse, before large split workspaces.** Preserve 64×64 output tiles; let a CTA consume neighboring *output tiles* with an explicit common operand panel retained across tiles, rather than doubling the accumulator or merely looping the old independent tile. Choose M-neighbor or N-neighbor reuse separately for gate and down. Device-local compiler-visible allocation; veto duplicate CTA output ownership or workspace that exceeds the existing budget. Controls: current unsplit, previous wider-tile loss, and **one leg only** split=2 if legal; independent FP32 oracle, BF16 final cast and full-step timing. A 15–25% saving of the measured 464 µs is **.070–.116 ms** if attainable; D768 already computes ~195 TFLOP/s useful per dW leg, so this is not a grid-starvation fix. Priority 1 touches the same gate-dW; do not add their claimed savings without the factorial.

The optimistic ends of those screening ranges still account for only ~.47 ms before interaction, versus .731 ms needed. They are discriminating experiments, **not a funded prediction of 1.2×**. To cross, for example, a *measured* .50 ms native-only cut plus .10 ms from shared would still require another .131 ms at fixed router, or .786 ms additional acceleration shared by both precisions. If the first two prototypes deliver less than .15 ms together in the whole graph, stop extrapolating to 1.2 on these geometries; pursue broader end-to-end redesign or accept the measured speedups. For tiny inputs a fixed .3596 ms measured router already uses ~94% of the .3814 ms target: that leaves ~22 µs for *everything else* in the additive thought experiment, versus ~149 µs native isolated FFNs. Hard selection alone was .2541 ms, transport fwd/bwd .0390/.0328, metadata step .0082. A general 1.2× on small inputs under the same semantics is not a credible acceptance requirement.

Keep the existing anchor in an eight-trial opening. Admit one legal candidate from each materially different family, one unfused control, protect one one-leg dW control when long-K, and substitute the existing short-K control when small. Rank by EC, rows per warp tile, K macro-stage count, logical prepared bytes, workspace and expected operand reuse; no SKU table or register shopping. Compare actual 8→32 on unseen packs; accept a family only after warm all-leaf whole F+B wins in alternating visits beyond variability, original FP64/changed-dY gates pass, and instance counts, peak/live memory and second-device portability are recorded. New launcher bodies should submit kernels only; let the compiler see allocations. No user streams or workspaces. No change to defaults, production code or accuracy gates was made here.

All eight completed probe records have the matrix source digest. GPU0 UUID `GPU-09db6472-cc08-c4cb-90db-560de232e5aa`; each job preflighted idle GPU0, no other device used. No power/clock changes. Exact-key trace union coverage 99.99% inside first-to-last-kernel span (not sum of overlapping durations). Its recorded whole-benchmark peak allocated was 1,101,811,200 bytes with five flat live samples; the width challenger also had zero postwarm growth. No new counters collected. Old isolated down counters and shared preparation diagnostics apply only to the original experiments, not these new stages. 5070 cross-budget drift and 5060 timing-ineligible results do not qualify 1.2×.

For example, in the repo, extract the archive to a fresh directory, set `P` to its `rtx-astra-1p2-20261119` subdirectory and `OUT` to a fresh output directory; rerun the exact-key experiment:

```bash
CUDA_VISIBLE_DEVICES=0 .venv/bin/python -m benchmarks.benchmark_moe_varlen \
  --source . --output "$OUT/keys.json" --case-id d768_e48_k6_h256 \
  --lengths 4097 8223 --max-autotune --expert-phases \
  --router-config "$P/d768-keys.router.json" --expert-config "$P/d768-keys.expert.json" \
  --shared-config "$P/d768-keys.shared.json" --rounds 3 --samples 7 \
  --phases mxfp8_step bf16_checkpoint_step router_step expert_step --trace-phases expert_step
```

The two native controls substitute the separate or wide-dW expert sidecar; the width run also used `--oracle`. For routing-only probes substitute the recorded case, lengths and router sidecar, with phases `router_step hard_forward transport_forward transport_backward metadata_step`. Sources, options, complete phase lists, rounds and individual measurements are in each JSON. Fresh-process comparisons here are diagnostic, not a runtime winner selection or proof of convergence.
